# 📘 README - Codexion

## 🧩 Description

**Codexion** is a concurrency simulation project written in C, inspired by the classic *Dining Philosophers* problem.
It models multiple threads (*coders*) competing for shared resources (*dongles*) while performing cyclic tasks such as compiling, debugging, and refactoring.

The main objectives of this project are:

* Understanding and managing **thread synchronization**
* Preventing concurrency issues such as **deadlocks** and **starvation**
* Ensuring precise timing and safe access to shared resources

---


## 🚫 Blocking Cases Handled

The following concurrency issues were addressed:

* **Deadlock Prevention:**
  Avoided Coffman’s conditions by enforcing a consistent resource acquisition order.

* **Starvation Prevention:**
  Ensured fair access to resources for all coders.

* **Cooldown Handling:**
  Introduced delays between resource usage to reduce contention.

* **Precise Burnout Detection:**
  Monitored each coder to detect failure (timeout) accurately.

* **Log Serialization:**
  Ensured thread-safe and ordered logging without output interleaving.

## 🔒 Thread Synchronization Mechanisms

The implementation relies on the following primitives:

### 🧵 `pthread_mutex_t`

* Protects shared resources such as:

  * dongles
  * simulation state
  * logging output

### ⏳ `pthread_cond_t`

* Enables thread coordination and signaling
* Allows threads to wait for specific conditions (e.g., resource availability)

### 🔄 Coordination Strategy

* Mutexes are locked before accessing shared data and unlocked afterward
* Condition variables are used to notify waiting threads when resources become available

### 🛡️ Race Condition Prevention

Examples:

* Protecting `last_compile_time` with a mutex
* Ensuring exclusive access to dongles

## 🧩 Priority Queue

### 📌 Definition

A **Priority Queue** is a data structure similar to a regular queue, but instead of processing elements in insertion order (FIFO), elements are processed based on their **priority**.

In other words:

* The element with the highest priority is served first
* It does not necessarily follow the order of arrival

---

### 🔁 Difference Between Queue and Priority Queue

#### 🟢 Queue (FIFO)

* First In → First Out
  Example:

```id="k2n8af"
A → B → C
```

Output:

```id="o9x1lm"
A then B then C
```

#### 🔵 Priority Queue

* Highest priority → served first
  Example:

```id="u3pt9r"
A (priority 2)
B (priority 5)
C (priority 1)
```

Output:

```id="d8z4qw"
B → A → C
```

---

### ⚙️ How It Works

Each element in a Priority Queue contains:

* A value (e.g., a coder)
* A priority (e.g., deadline or time constraint)

The queue automatically orders elements based on their priority.

---

### 🧠 Usage in Codexion

The Priority Queue is mainly used with the scheduling algorithm:

### ⏱️ EDF (Earliest Deadline First)

Where:

* Each coder has a `deadline`
* The system selects the coder with the **earliest deadline**

#### 📊 Example:

| coder | deadline |
| ----- | -------- |
| A     | 100 ms   |
| B     | 50 ms    |
| C     | 200 ms   |

📌 Order:



```id="g7h2ds"
B → A → C
```

### 🔄 Role of the Monitor

The **Monitor Thread** is responsible for:

1. Collecting coders requesting resources (dongles)
2. Inserting them into the Priority Queue
3. Selecting the next coder based on:

   * EDF (earliest deadline)
   * or FIFO (if no priority scheduling is used)

---

### 🔧 Implementation in C

#### 1. Sorted List

* Insert elements in order
* Simple but less efficient

#### 2. Heap (Recommended)

* Typically a **Min Heap** for EDF
* Efficient operations: `O(log n)`

---


### 🛡️ Benefits

Using a Priority Queue allows:

* Efficient resource scheduling
* Reduced waiting time
* Starvation prevention
* Better handling of real-time constraints

---

### 🔥 Summary

* Priority Queue = queue ordered by priority
* In EDF: priority = earliest deadline
* The Monitor manages it and decides which coder runs next


### 🤝 Communication Between Coders, Monitor, and Watcher

The simulation relies on a clear separation of responsibilities between threads to ensure correct and efficient behavior:

* **Coders (Worker Threads):**
  Each coder performs its tasks (compile / debug / refactor) and updates its own state (such as `last_compile_time` and `compile_count`) in a thread-safe manner using mutexes.

* **Watcher Thread (Burnout Detection):**
  The watcher is responsible for detecting burnout conditions. It continuously monitors time constraints to ensure that no coder exceeds `time_to_burnout` without performing a compile operation.

* **Monitor Thread (Scheduler):**
  The monitor is responsible for coordinating access to shared resources (dongles) using a scheduling algorithm such as:

  * **FIFO (First In, First Out)**
  * **EDF (Earliest Deadline First)**

  The monitor manages the queue of coders and determines which coder gets priority to access resources.

---

### 🔄 Synchronization Strategy

* Shared resources (dongles, queue, global state) are protected using `pthread_mutex_t`
* Coders request access to resources through a structured queue
* The monitor manages this queue based on the selected scheduler (FIFO or EDF)
* `pthread_cond_t` is used to wake up coders when resources become available

---

### 🛡️ Race Condition Prevention

* All shared data (queue, dongles, global state) is protected with mutexes
* Exclusive access to dongles is guaranteed for each coder
* Logging is serialized to prevent interleaved output

---

### ⚠️ Design Clarification

* **Burnout detection** is handled exclusively by the watcher thread
* **Resource scheduling** is handled exclusively by the monitor thread

This separation of concerns improves:

* Code clarity
* Reduced complexity
* Easier debugging and maintenance

## Overview

This project implements a **circular scheduler queue** where each coder knows its position and its direct neighbors (left and right) using queue indices.

---

## Data Structure

Each coder contains:

* `id` : the unique identifier of the coder
* `index_in_queue` : the position of the coder in the queue
* `|| 1 1 / 0 0` : indicates the state of the dongle (active or inactive)
* `left_index` : the index of the previous coder in the circular queue
* `right_index` : the index of the next coder in the circular queue
